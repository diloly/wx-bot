## xlog 解码器落地（11:15，用户选"继续探 xlog 内存只读取密钥"）
- WebSearch 查到关键事实：**腾讯 mars 官方 `decode_mars_crypt_log_file.py` 把服务端私钥硬编码成公开常量**（`PRIV_KEY=145aa7717bf9745b91e9569b80bbf1eedaa6cc6cd0e26317d810e35710f44cf8`），曲线 secp256k1。故 xlog TEA 密钥 = `sha512(ECDH(服务端私钥, 块头客户端公钥))[:16]`，**纯文件即可解，无需扫进程内存**（之前"密钥只在内存"结论只对一半）。
- 块结构（magic=0x07, crypt_key_len=64）从官方源码对齐：headerLen=73=`[0]magic+[1:3]seq+[3]begin_hour+[4]end_hour+[5:9]length(uint32)+[9:73]64B客户端公钥`，其后 length 字节 TEA 密文，末尾 0x00。用户那条 `07 01 00 09 09 F6 00 00 00` 完美对上（seq=1, hour=9, len=0xF6=246）。
- TEA 算法：mars 自定义 16 轮，`s=(delta<<4)`，每轮 `s-=delta`；tea_decrypt 按 8 字节分组解密（末组不足补原字节）。已逐行对齐官方 `tea_decipher/tea_decrypt`。
- pyelliptic `get_ecdh_key` 返回 512bit=sha512(共享点x坐标)64字节（pybitmessage 文档证实）；TEA 取前 16 字节。用 `cryptography` 库复刻（exchange 返回 32字节 x 坐标 → sha512[:16]），避开老旧 pyelliptic。
- 交付 `xlog_decode.py`（纯只读文件解码，不碰进程/不注入）：自动找最新 `mm_*.xlog` 或指定路径，输出 `<名>.decoded.log` + 前40行预览。依赖 `pip install cryptography`。
- 待用户本机跑：若解出来是可读日志→成功；若 `[!] zlib 解压失败`→说明本机微信换了服务端密钥/偏移，需改走"扫进程内存取 tea_key_"兜底（LogCrypt.tea_key_ 字段，偏移待该版本确认）。
- **重要风险提示**：即使解成功，xlog 多为调试/流水账，未必含聊天正文；需看明文确认有无消息文字。

## xlog 格式与解密可行性（11:10，WebSearch 查证）
- 微信 xlog 是 **mars xlog** 格式，每个日志块首字节是 magic：本机文件首字节 `07` → **TEA 加密 + 压缩**（magic 表：03/04/05/06=XOR，07=TEA+压缩，08/09=无加密）。确认我们的 `mm_*.xlog` 是 TEA 加密块。
- **致命点：密钥不在文件里。** mars xlog 用 ECDH+TEA：每次启动微信随机生成 client 密钥对，ECDH 协商出会话密钥后**丢弃 client_priv**，只有 client_pub 附在每块块头。无服务端私钥则纯文件解码**数学上不可能**（社区共识 + 吾爱破解实测）。
- **但密钥存在于正在运行的微信进程内存里**：`LogCrypt` 对象含 `tea_key_`(会话TEA密钥, 16B, 距对象+0x0C) 与 `client_pubkey`(64B, +0x1C) 相邻。逆向手法：从 xlog 块头(73字节, magic=0x07)取当前 epoch 公钥 → ReadProcessMemory 扫 Weixin/WeChatAppEx 进程内存定位该64字节 → 邻域即 tea_key_ → 用 TEA 密钥解密块+zlib 解压得明文。此过程**只读进程内存、不注入不改微信**，属"非侵入"但非"纯文件解码"。
- **更大风险**：xlog 内容是调试/流水账日志（网络/UI/错误），**大概率不含聊天正文**（对方发来的消息文本未必进日志）。即使得出明文也可能没有我们要的"客户回复"。
- 结论：用户选的"解 xlog（只读）"实际需"内存只读取密钥+解块"，且产出可能无聊天文字。需向用户摊牌此约束再决定是否投入写解码器。
